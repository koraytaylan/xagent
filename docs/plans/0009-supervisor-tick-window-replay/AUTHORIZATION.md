# Authorization record: 0009-supervisor-tick-window-replay

## Amendment 1: INV-5 per-pin cap (task tick-window-core)

- **Superseded requirement:** ARCHITECTURE.md INV-5 read "Frames inside `[t - H, t + H]` of every retained replacement-boundary or season-flip pin survive rolling eviction, both in memory and on disk", which review read as requiring every in-range frame to survive.
- **Contradiction:** INV-3 (ARCHITECTURE.md) holds at most `max_frames_per_pin` frames per pin, and the tick-window-core packet prune rule (tasks/0101-tick-window-core.md, prune step 1) marks only the first `max_frames_per_pin` in-range frames sorted by `(distance, tick)`. With the frozen `PIN_HALF_WINDOW_TICKS = 2_000`, `MAX_FRAMES_PER_PIN = 512` and one frame per tick, a pin range can hold 4,001 frames, so no implementation can satisfy all three as worded.
- **Correction:** INV-5 now states that the nearest `max_frames_per_pin` frames (by distance, then tick) inside `[t - H, t + H]` of every retained pin survive rolling eviction in memory and on disk, and that in-range frames beyond the cap are not protected by the pin. This matches the prune rule, INV-3, the loader LIMIT `max_frames + max_pins * max_frames_per_pin + 1`, and 0201's INV-5 proof (at least one frame in range). No constant, task, dependency, check or gated flag changed.
- **Executable witness:** check `focused-proof` (`cargo test -p xagent-sandbox --lib tick_window`) of task tick-window-core, through `tick_window_pinned_frames_survive_rolling_eviction`, `store_disk_pins_survive_rolling_eviction` and the per-pin cap test (INV-3), with the implementation's overflow test `store_disk_keeps_nearest_capped_frames_when_pin_range_overflows` showing the nearest cap-many in-range frames survive in memory and on disk.

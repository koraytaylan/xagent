**Question under review:** On 1× the system sustains the expected 60 tps with linear scaling through 100× (6 k tps). At 1000× the observed ceiling is ~20 k tps instead of the proportional 60 k tps. ## Executive Summary

The observed behavior is exactly explained by the current architecture: the simulation worker caps every dispatch to one kernel-batch (default vision_stride=10 × brain_tick_stride=10 = 100 physics ticks). Each such batch produces one wgpu CommandEncoder, one uniform upload (which allocates a fresh `vec![0.0f32; 24]` inside `build_world_config`), four compute-pass recordings (prepare + fused kernel + global + indirect vision), and one `queue.submit`. The tight worker loop (no sleep while backlog) therefore sustains a maximum batch submission rate limited by CPU + driver overhead of command recording and submission.

On the test hardware (macOS/Metal), this sustains roughly 200 batches per real second. 200 × 100 = 20 k ticks/sec — the exact ceiling reported. Because the per-batch work is almost entirely fixed overhead (encoder creation, bind-group setup, small writes, submit, plus two unconditional `device.poll(Poll)` calls per iteration from the two collect sites, plus occasional 60 Hz / 30 Hz copy-submits for snapshots and telemetry), the achieved rate is insensitive to agent count for small populations (N=4 vs 10). The kernel dispatch itself (`dispatch_workgroups(agent_count,1,1)`) and the global 1×1 pass are negligible; GPU execution time per batch is << submission overhead.

At 1×–100× the required batch rate (≤60 batches/sec) is low enough that the accumulator logic + 1 ms `RUNNING_SLEEP` when not immediately dispatchable allows the worker to match wall-time × multiplier without ever entering the pure max-rate tight loop; sleeps + measured `dt` produce the linear, correct tps. At 1000× the required rate (600 batches/sec) exceeds what the submission loop can sustain even with zero sleep, so the accumulator caps, the loop spins at hardware-limited ~200 batches/sec, and tps plateaus at ~20 k. Snapshot publication remains throttled to 60 Hz wall time independently (`STATE_SNAPSHOT_MIN_INTERVAL`), so tps display (computed from delta ticks between arriving snapshots over 1 s wall windows) faithfully reports the worker's actual progress.

Main-thread costs (apply_state_snapshot O(N), history deque pushes, trail/heatmap sampling, hud/instance rebuilds, egui) are also snapshot-rate limited (~60 Hz) rather than tick-rate limited and are tiny for N=10; they do not throttle the worker. Generation handoffs (fitness + DB + ResetPopulation) occur only at budget boundaries and pause the sim during the handoff; they affect long-term average but not the peak sustained tps inside a generation. Recording (if enabled) also samples at publication cadence, not sim-tick cadence.

The design intent (README, backpressure spec, CONTRIBUTING) that "achievable throughput is GPU-bound" and "per-tick CPU cost ... small at any throughput" holds for large agent counts or when vision/global work dominates, but is not true for the default small population used in the reported measurements. The fixed per-batch submission tax becomes the limiter before GPU saturation is reached. No per-tick Rust simulation logic exists (good), no large clones in the steady-state hot path (good), throttle consumption is correctly conditional (good), but the batch submission rate itself is the unamortized cost that the current 100-tick chunk size + one-submit-per-chunk policy exposes at extreme multipliers.

## The Core Path: Worker Loop → Accumulator → One-Batch Dispatch

The worker thread owns cadence (sim_runtime.rs:703):

```rust
loop {
    ... drain commands via try_recv ...
    let busy = worker.step(event_tx);
    if !busy { std::thread::sleep(idle_sleep()); }  // 1 ms running, 8 ms paused
}
```

`step` (463) always does collection + the two throttled requests, then (if not paused) `advance_compute(dt)`.

`advance_compute` (518) is the heart of speed scaling:

- `sim_accumulator += dt * speed_multiplier as f64`
- cap accumulator to `sim_delta_time * max(speed*3.0, min_dispatch+2)`
- `raw_ticks = floor(accum / dt).min(dispatch_cap)` where `dispatch_cap = kernel.kernel_batch_size() = 100`
- only dispatch if `>= brain_tick_stride (10)`
- `kernel.dispatch_ticks(...)`  (always ≤100 ticks for worker-initiated calls)
- `accum -= ...`; advance counters; return true → no sleep

When the required rate exceeds the loop's dispatch cadence, `accum` stays high (capped), `dispatched` is always true, the loop becomes a pure spin submitting as fast as the CPU path allows. Measured `dt` per spin iteration is exactly the wall time of one "create encoder + 4 passes + submit + polls + bookkeeping".

Default batch = 100 ticks (config.rs:163-169, kernel creation 484). Thus 60 k tps target ⇒ 600 submissions/sec; 20 k tps observed ⇒ ~200 submissions/sec sustainable.

## Per-Batch Overhead in `dispatch_ticks` (gpu_kernel.rs:1354)

For a worker call with exactly 100 ticks (the normal case):

- `brain_cycles = 10`, `kernel_batches = 1`, `remainder_cycles=0`, `total_batches=1`
- loop once:
  - `upload_world_config_with_cycles` (1146) → `build_world_config` (buffers.rs:418) does `let mut wc = vec![0.0f32; 24];` (alloc every batch), fills 20+ scalars, `queue.write_buffer` to the active ping-pong uniform
  - `device.create_command_encoder(...)` (label "dispatch_kernel")
  - begin_compute + set + dispatch(1,1,1)  // prepare indirect args
  - begin_compute + set + dispatch(agent_count,1,1)  // the fused kernel (physics+food+brain inner loop over vision_stride)
  - begin_compute + set + push + dispatch(1,1,1)  // global (grid + 3× collision passes)
  - begin_compute + set + dispatch_indirect  // vision
  - `queue.submit( once(encoder.finish()) )`
- after loop: flip `active_config_index`
- (no physics remainder when exact multiple of stride)

Result: 1 Vec<f32> allocation, 1 small write_buffer, 1 encoder, 4 compute pass recordings, 1 submit per 100 ticks. This is the "per-dispatch overhead" the batching was meant to amortize; at 600 Hz it is no longer small in absolute terms.

The comment at 1361-1363 explains why separate submits per kernel-batch even inside a larger `dispatch_ticks` call: uniform visibility for the per-batch `cycles_this_batch` override that controls the inner shader loop. The worker never exercises >1 kernel-batch per `dispatch_ticks` call, but the path still pays per-batch.

## Additional Fixed Costs per Worker Iteration

- `try_collect_state_snapshot` (1543): `device.poll(wgpu::Maintain::Poll)` + `try_collect_staging` (loop over all 6 STAGING_SLOTS, atomic status checks, occasional get_mapped_range + Vec clear+extend + unmap when a 60 Hz snapshot lands)
- `try_collect_telemetry` (2135): **another** `device.poll(Poll)` + pending check (even when no telemetry in flight)
- `maybe_request_state_snapshot` (564): elapsed check against 16.6 ms; when due (~60/s) may do another encoder + copy_buffer_to_buffer (phys + optional food) + submit + tracker reset + 1-2 map_async installs (1486)
- `maybe_request_telemetry` (642): similar, ~30/s, up to 4 copy_buffer_to_buffer + submit + ReadbackTracker::new(4) + installs (request fn 2044 also has its own pending gate)
- counters, occasional log (1 Hz)

Thus at max rate: ~2 polls + status work + ~200 main submits + ~60 snapshot copy submits + ~30 telemetry copy submits per real second. All independent of agent count (the copies are O(1) or O(food) for snapshots).

Snapshot publication itself uses try_send into bounded channel (EVENT_CAPACITY=256); drops are intentional latest-wins (633). Publish rate is deliberately publication-rate limited, not tick-rate limited.

## Main-Thread Snapshot Consumption Is Not the Limiter

RedrawRequested (main.rs:453) runs at display rate (typically 60–120 Hz via winit request_redraw + present). It does:

- `drain_sim_events` (gpu_orchestration 157) → partition (scans small Vec), at most one apply per frame
- `apply_state_snapshot` (206): O(N) scalar copies for 10 agents (~30 fields each), food clone_from (small), tps_tick_count += delta, sets 3 dirty flags, hud/snap dirty
- `on_fresh_snapshot` (298): `record_overlays_and_histories` (snapshot.rs:50) which for N=10 does heatmap cell inc + dist check + optional push (trail), plus 6 deque push/pops per agent for sparklines (capped 10k)
- throttled (100 ms) mesh rebuilds for food/trails (render_pipeline 142), heatmap when enabled, selection marker (always)
- `update_agent_instances` (234) gated on hud_dirty (set every snapshot): builds Vec<10 InstanceData>, one write_buffer
- `rebuild_hud_text` (278) gated on hud_dirty: builds bars + TextItem vec
- full egui + 3D render (one combined submit + present per frame)

All of the above are O(1) or O(N=10) and run at ~60 Hz wall time because they are driven by snapshot arrival rate (or the 10 Hz throttles), not by simulated ticks. They add fixed CPU/GPU work per real second; they do not slow the background worker's dispatch loop. The worker continues submitting compute while the main thread is in egui or rebuilding a trail mesh.

tps_display (snapshot.rs:163) is recomputed on the main thread from the deltas carried by the (60 Hz) snapshots over 1 s wall windows. It therefore reports the true rate at which the worker advanced `tick`, even if main thread frame rate varies.

## Generation Handoffs, Recording, and DB Are Boundary Costs

`on_generation_budget_reached` and `finish_generation_continue` (evolution.rs) run only when `gen_tick` crosses the budget (worker forces a blocking snapshot read, pauses itself, emits control event). The main thread then:

- gov.evaluate (O(N) + composite_fitness)
- gov.log_generation / store_recording (DB writes, potentially large blob if recording enabled)
- spawn_population, build_pending_upload (clones of terrain grids, food lists, agent tuples)
- send ResetPopulation (boxed)
- later on_champion_state → worker reset (may do try_reset spin or full kernel rebuild + batch_write_agent_states with clones for mutants)

These pause the sim (pending_generation makes desired_paused true) for the duration of the handoff. At 20 k tps a 10 k-tick generation lasts ~0.5 s wall; handoff overhead of tens of ms reduces long-term average but the peak rate inside the generation (what the 20 k number reflects) is still the dispatch-limited rate. Reducing N from 10→4 would shrink evaluate/upload/clone costs, yet produced "no change," confirming the ceiling is inside the steady-state dispatch loop, not the boundary.

Recording (replay_coord + replay.rs) samples at snapshot cadence (extend_from_slice of ~10 TickRecords per 60 Hz), not per simulated tick. Memory growth is therefore wall-time bounded, not multiplier bounded. The comment in record_replay_tick explicitly acknowledges the decoupling.

## Alignment With (and Minor Drift From) Stated Rules and Design Claims

CONTRIBUTING.md Performance:

- "Per-tick simulation logic belongs in WGSL" — strictly true in the steady path.
- "No CPU-side work should scale with `ticks_to_run`" — the worker respects the 100-tick cap per advance call; the internal budget is small (the 3×speed accumulator cap). The 500/64 k numbers in older comments and bench are stale relative to the 100-tick kernel-batch reality.
- "Never clone large collections in per-frame hot paths" — holds for the worker (small to_vec of cached state on the 60 Hz publish path only) and for main (snapshot-driven, throttled rebuilds).
- Throttle windows consumed only on actual work — snapshot request throttle is correct; mesh rebuilds are correct.

README claims (around 1089, 977):

- "achievable throughput is GPU-bound, not redraw-bound" — true for redraw, but for the N=10 regime the limit is CPU command-submission overhead, not GPU execution time or queue back-pressure from the device. The assumption that "per-dispatch overhead" is successfully amortized at 100-tick granularity breaks when the target dispatch rate exceeds ~200/s.
- "Per-simulated-tick CPU cost is the world-config uniform write + command-encoder setup, divided by the batch size — small at any throughput" — the *per-tick* cost is indeed tiny; the *absolute* cost of sustaining the required number of "write + encoder + submit" operations per second is not.

The 2026-04-13 backpressure design correctly identified the old coupled problems and introduced the 6-slot ring + decoupled 60 Hz publication + worker thread. It enabled the linear regime up to 100×. The current ceiling is the next natural limit once the old back-pressure pathologies were removed.

## Why Agent Count Did Not Matter

- Kernel dispatch shape: (agent_count,1,1) workgroups. For N=4 vs 10 the difference in launched threads (1024 vs 2560) and per-workgroup brain math (fixed 256 threads doing vision 48 rays + 7 coop passes) is tiny on a modern GPU; launch + execution time << Metal command-buffer commit + wgpu encoding overhead.
- Global pass: 256-thread workgroup doing fixed-size grid clears + food grid + only `if (tid < agent_count)` for agent grid/collision. For N<<256 this is effectively constant time.
- All snapshot/telemetry copies, Vec builds on main, history pushes, instance uploads etc. are also O(N) or O(1) with tiny constants.
- Hence the rate-limiting step (command recording + submit in the worker spin) is the same for both populations.

At substantially larger N (hundreds), the kernel and especially vision raycast + per-agent food-detect (brute over ~200–400 food items inside the 256-thread workgroup) + collision would start to dominate wall time per batch, the achieved max tps would drop, and further N reduction would help. The reported experiment stayed in the "overhead-bound, not compute-bound" regime.

## Minor Secondary Observations (Not the Root Cause)

- Double `poll(Poll)` per iteration (state collect + telemetry collect) even when no readback pending. Could be made conditional on `any(staging_in_flight) || pending_telemetry.is_some()`.
- Fresh `vec![0.0; 24]` on every batch inside build_world_config. Could pre-allocate a reusable array or &mut buffer in the hot path.
- Telemetry copy submit still occurs at 30 Hz even at extreme sim rates (where the single selected agent's charts do not need 30 updates/sec of wall time).
- In `dispatch_ticks` the physics-remainder path and the multi-batch loop inside one call are exercised only by bench/old paths or non-multiple calls; worker path is clean 1-batch-1-submit.
- `STAGING_SLOTS=6` + request dropping when full is working as designed; at the observed rates slots are not the limiter.
- Main-thread hud_dirty is set on every snapshot arrival (gpu_orchestration:274) even though the expensive mesh/instance work is separately throttled or gated; this causes cheap but unnecessary per-frame checks.

## Summary of the Bottleneck Location

**Primary:** `sim_runtime::Worker::advance_compute` (when backlog) → `GpuKernel::dispatch_ticks` (single kernel-batch case) → `create_command_encoder` + `upload_world_config_with_cycles` (vec alloc + write) + 4×`begin_compute_pass` + `queue.submit`, executed in a zero-sleep spin whose iteration rate determines max tps (100 ticks per iteration).

**Contributing fixed costs:** double poll, 60/30 Hz snapshot/telemetry copy submits, small bookkeeping.

**Not involved at the limit:** agent-count work in the shader, main-thread render or snapshot apply (they run at fixed wall Hz), generation handoff (boundary only), large clones, per-tick Rust work, staging slot exhaustion.

The 20 k tps / 200 batches-per-sec number is a property of the current wgpu/Metal command-path cost for this particular encoder shape on the hardware, exposed once the old coupled bottlenecks were removed and the target multiplier pushed the required submission rate past what the per-batch tax can support for the default (small) population.

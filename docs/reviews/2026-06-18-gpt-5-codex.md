## Executive Summary

The implementation is broadly well-covered by tests, and the full workspace test
and clippy gates pass. The risky part is not compilation or basic GPU execution.
The risky part is the new Plan 0009 validation gate.

The generated speed-decoupling decision currently says the speed-fitness
correlation **rose** from baseline to ON, but still marks the gate PASS. The
harness also runs baseline and ON with different random mutations and stochastic
brain-state mutations, so the A/B is not controlled enough to justify flipping
defaults. This is the same class of problem called out in previous reviews:
selection and performance conclusions must be tied to discriminative,
on-target measurements rather than plausible-looking summaries.

## Findings

### P1: The Speed-Decoupling Gate Can Pass Even When The Primary Metric Gets Worse

**Impact:** The Plan 0009 default-flip gate can approve `speed_cost_exponent > 1`,
`effort_rebased_fitness = true`, and `danger_percept_enabled = true` even when
the ON run does not improve the stated speed-fitness criterion. This can promote
a configuration based on an internally contradictory decision record.

**Evidence:**

- `crates/xagent-sandbox/src/headless.rs:976-980` defines the gate as:
  `abs(on_speed_fitness_correlation) < 0.3` plus viability and danger retention.
  It does **not** require the baseline correlation to be strongly positive, does
  **not** require ON to be lower than baseline, and does **not** fail when ON
  correlation rises.
- `docs/plans/0009-Intent-Aware-Fitness/0009-SPEED-DECOUPLING.md:16` records
  baseline `0.2238`, ON `0.2569`, delta `+0.0331`.
- The same decision doc then says the correlation "rose" at line 37, but line 67
  still marks "Speed-fitness correlation falls from strongly-positive to approx
  0" as PASS, and lines 73-77 declare the gate passed.

**Why this matters:** The criterion text and the code disagree. If the intended
criterion is "falls from strongly-positive to approximately zero", the current
run fails the "falls" part and probably also fails the "strongly-positive
baseline" part. If the intended criterion is only `|r_on| < 0.3`, the report text
overstates what was proven.

**Recommendation:** Make the gate match the decision rule:

- Require a minimum exploitable baseline signal, for example
  `baseline_r >= baseline_min`.
- Require improvement, for example `on_abs <= baseline_abs - min_delta`, or at
  least `on_abs < baseline_abs`.
- If the baseline is already weak, report "inconclusive" rather than PASS.
- Regenerate `0009-SPEED-DECOUPLING.md` only after the corrected gate runs.

**Previous-report overlap:** This repeats the measurement-validity theme from
`2026-06-15-brain-pass-latency-ceiling.md`, where the prior CPU-submission
conclusion was superseded by direct measurements. It also overlaps with
`2026-06-14-claude-opus-48.md`, which warned that weak/noisy selection signals
can make evolution look meaningful while actually moving on noise.

### P1: The Validation Harness Does Not Run A Controlled Baseline vs ON A/B

**Impact:** The generated Plan 0009 validation metrics are not reproducible
enough to support a default flip. Baseline and ON are not just different flag
settings; they also get different random genomes, brain resets, and inherited
state mutations.

**Evidence:**

- `crates/xagent-sandbox/src/headless.rs:423-428` runs baseline first and ON
  second in separate calls to `run_headless_with_flags`.
- `crates/xagent-sandbox/src/headless.rs:543-545` seeds each initial population
  with `mutate_config(&seed_config)`.
- `crates/xagent-sandbox/src/agent/mod.rs:378` uses `rand::rng()` inside
  `mutate_config_with_strength`, so baseline and ON get different starting
  genomes.
- `crates/xagent-sandbox/src/headless.rs:616` calls `kernel.reset_agents(...)`,
  whose reset path uses a fresh random RNG.
- `crates/xagent-sandbox/src/headless.rs:623` mutates inherited brain state, and
  `crates/xagent-sandbox/src/agent/mod.rs:500` again uses `rand::rng()`.

**Why this matters:** A/B validation needs paired randomness or fixed seeds. As
written, observed deltas can be caused by stochastic population composition or
brain-state mutation, not the 0009 flags. This is especially serious because the
current measured deltas are small on the primary correlation axis.

**Recommendation:** Make the validation deterministic and paired:

- Use a seeded RNG for initial config mutations and inherited brain mutations.
- Generate one population/genome schedule and replay it under both flag sets.
- Record the seed and generation count in the markdown output.
- Prefer per-generation paired deltas over one flattened aggregate correlation.
- Keep temporary DB cleanup complete by removing `-wal` and `-shm` files too.

**Previous-report overlap:** This is the same statistical-control issue as the
`2026-06-14-claude-opus-48.md` finding that eval noise exceeded selectable
signal. It also matches the `2026-06-12-gpt-5-codex.md` recommendation to measure
operational learning signals directly rather than infer them from noisy
aggregate outcomes.

### P2: Fused Avoidance-Intent Counters Use Previous-Cycle Danger Bearings

**Impact:** `avoidance_intent_fraction` is a new gate metric, but in the fused
kernel it is recorded from stale nearest-danger slots. The metric can miss the
first in-range tick, count an extra stale tick after leaving danger range, and
attribute "turn away" against the previous danger bearing. This weakens the
danger-retention evidence used by the Plan 0009 gate.

**Evidence:**

- In `crates/xagent-brain/src/shaders/kernel/kernel_tick.wgsl:790-805`, fused
  cycle order is:
  `agent_physics(...)` loops over physics sub-ticks, then `agent_food_detect`,
  then `agent_danger_detect`.
- Inside `agent_physics`, the avoidance counters are updated at
  `kernel_tick.wgsl:246-260` by reading `P_NEAREST_DANGER_DISTANCE` and
  `P_NEAREST_DANGER_BEARING`.
- Those slots are only refreshed later by `agent_danger_detect` at
  `kernel_tick.wgsl:269-334`.
- The split physics shader does the opposite: it scans current danger first at
  `phase_physics.wgsl:197-247`, then increments avoidance counters at
  `phase_physics.wgsl:249-260`.

**Why this matters:** The brain shaping path is current, because the fused brain
reads danger after `agent_danger_detect`. The observability metric is the stale
part. Since `avoidance_intent_fraction` appears in the validation report and
default-flip criteria, this is not just cosmetic.

**Recommendation:** Move avoidance-intent accumulation to a point after fused
`agent_danger_detect`, or pass the current danger result into a helper that both
sets nearest-danger slots and increments the counters. Add a fused GPU test that
places danger on one side for exactly one tick and asserts the counter/bearing
use the current tick, not the prior one.

**Previous-report overlap:** This is a direct recurrence of the temporal
alignment concern from `2026-06-12-gpt-5-codex.md`, where sensory evidence and
homeostatic consequences were found to be misaligned. Here the misalignment is
in the new danger-intent telemetry.

### P2: Validation Uses Different Danger Metric Reductions Than Production Persistence

**Impact:** The validation report and the governor database can disagree on the
same behavior metric. That makes it harder to compare headless validation output
to production run history.

**Evidence:**

- Production persistence aggregates first:
  `governor.rs:831-844` computes
  `sum(danger_path_length) / sum(distance_traveled)` and
  `sum(avoidance_turns_opposing) / sum(avoidance_sense_range_ticks)`.
- Validation averages per-agent ratios:
  `headless.rs:790-820` computes each agent's danger fraction and avoidance
  fraction, then takes an unweighted mean. For avoidance, `sense_ticks.max(1.0)`
  also changes zero-exposure handling.

**Why this matters:** A run with one highly exposed agent and many unexposed
agents can produce a different validation value than the persisted population
aggregate. Since the validation doc claims to be the canonical baseline for
future Plan 0009 A/B tests, the metric should match production semantics.

**Recommendation:** Reuse the same aggregate reducer for both paths. If both
weighted and unweighted metrics are useful, emit both with distinct names.

**Previous-report overlap:** This is another measurement-consistency issue. It
relates to `2026-06-14-claude-opus-48.md`, which found that the production path
and side-tool instrumentation did not expose the same within-lifetime learning
evidence.

### P3: Layout-Aware Flags Are Bypassed By Convenience Buffer Helpers

**Impact:** Runtime `GpuKernel` uses layout-aware APIs, so the current app path is
not broken. The public helper APIs are still traps: passing a flagged
`BrainConfig` to `build_config()` or `init_brain_state()` silently derives a
flag-off layout.

**Evidence:**

- `crates/xagent-brain/src/buffers.rs:809-813` implements `build_config(config)`
  with `BrainLayout::new(config.vision_width, config.vision_height)`, which
  ignores `visual_cortex_enabled` and `danger_percept_enabled`.
- `crates/xagent-brain/src/buffers.rs:722-726` does the same for
  `init_brain_state(config, rng)`.
- The correct runtime path uses `BrainLayout::from_config` and
  `build_config_for(..., &self.layout)` in `GpuKernel`, so this is isolated to
  helper/API use and tests.

**Recommendation:** Change the convenience wrappers to use
`BrainLayout::from_config(config)`, or rename them to make the legacy/default
layout explicit. Add a small unit test asserting that `build_config()` reports
`feature_count == BrainLayout::from_config(&config).feature_count` when the
danger percept flag is on.

**Previous-report overlap:** This is a continuation of the layout/taxonomy
hazard around locked runtime dimensions mentioned in earlier plan/status docs
and reinforced by `2026-06-15-brain-pass-latency-ceiling.md`: runtime constants
and measurement paths need a single source of truth.

The code is not in a failing build state. The serious issue is that Plan 0009's

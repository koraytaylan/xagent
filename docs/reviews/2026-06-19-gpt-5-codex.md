## Executive Verdict

XAgent is materially healthier than the April 2026 architecture snapshot and more instrumented than the June 2026 review set. The runtime story has converged around `GpuKernel`, docs now acknowledge most fixed/proxy configuration surfaces, Rust gates are green, and recent work added useful hardening around danger metrics, metabolic accounting, plan-reference guards, and validation criteria.

The project is still not ready to be treated as a low-touch maintenance effort. The biggest remaining risk is not basic code quality; it is scientific validity. Several recent changes encode stronger tests around the current behavior, but the behavior being protected is not always aligned with the original goal. The most important example is the new effort-rebased fitness: it claims duration independence, but the implementation still scales with survival length and leaves camper behavior highly competitive. The second major risk is validation rigor: the speed-decoupling A/B harness was made more paired at generation zero, but later-generation breeding still uses unseeded randomness, so the multi-generation result remains noisy and only partly reproducible.

Forward effort should be estimated as medium-high for the next quarter. Sustained progress needs Rust, GPU/WGSL, evolutionary simulation, statistics/experiment design, and enough product judgment to keep the project from drifting into optimizing proxy scores. The project is closer to its original architectural goal than it was in April, but still far from proving its original behavioral goal of robust emergent cognition through homeostasis and predictive processing.

## Detailed Findings

### F1 - P1 - Effort-Rebased Fitness Still Leaks Duration And Rewards Camping

**Evidence**

`crates/xagent-sandbox/src/governor.rs` documents the effort mode as duration-independent:

```rust
/// Foraging = food / (energy / ticks_alive)
/// Exploration = min(coverage, cells_explored / (distance / ticks_alive) / TARGET)
///
/// This rewards food found per unit energy rate and area covered per unit movement rate,
/// making scores independent of simulation duration while penalizing metabolic waste.
```

The actual implementation divides cumulative numerators by per-tick denominators:

```rust
let per_tick_energy = telemetry.energy_spent / ticks;
let foraging = (telemetry.food_consumed as f32 / per_tick_energy / EFFORT_FORAGING_TARGET).clamp(0.0, 1.0);

let per_tick_distance = telemetry.distance_traveled / ticks;
let cells_per_distance_rate = telemetry.cells_explored as f32 / per_tick_distance;
```

That means the ratios are effectively:

```text
food_consumed * ticks_alive / energy_spent
cells_explored * ticks_alive / distance_traveled
```

The decision note under `docs/plans/0010-Intent-Aware-Fitness-Hardening/0010-FITNESS-RECALIBRATION-DECISION.md` recognizes this explicitly for exploration: two agents with the same `cells_explored` and `distance_traveled` get different scores if one lived longer.

The focused replay now pins this outcome:

```text
Competent Forager Effort 0.3209
Fast-Aimless Effort 0.1343
Camper Effort 0.8646
```

So the recent hardening makes the competent profile beat fast-aimless, but it still scores far below camper. The camper score is unchanged from legacy in the replay.

**Why It Matters**

This is the most important due-diligence issue because it can make the project look healthier while still optimizing an unintended proxy. The stated goal is not "survive longest while barely moving"; it is to discover competent foraging and danger-aware behavior under homeostatic pressure. A score where a synthetic camper beats a competent forager by a large margin is not a reliable graduation criterion for default-flipping `use_effort_fitness`.

**Prior-Report Comparison**

The 2026-06-18 reviews criticized the previous 0009 effort fitness because it could collapse axes, miscalibrate real telemetry, and leave camping insufficiently penalized. Plan 0010 addressed part of that by adding replay fixtures, metabolic accounting, and revised targets. However, the new replay now hard-codes a result where camper remains strongest. The prior concern was reduced in one dimension, but not resolved.

**Recommended Path**

- Decide the intended invariant first:
  - If the score should be rate-based, use rate/rate comparisons consistently.
  - If it should reward total accomplishments, stop claiming duration independence and add explicit anti-camping constraints.
- Add a focused invariant test where two agents have identical rates over different lifetimes. The normalized effort axes should match unless survival is intentionally part of that axis.
- Add a ranking test that the baseline competent-forager profile beats the camper profile, or document why the project intentionally prefers camper behavior.
- Do not default-flip effort fitness until the ranking and duration invariants match the stated goal.

### F2 - P1 - Speed-Decoupling Validation Is Only Partially Paired

**Evidence**

Recent changes seed some validation arms in `crates/xagent-sandbox/src/headless.rs`, including initial configuration mutation, reset behavior, and inherited brain mutations. This is a real improvement.

However, the validation loop still calls:

```rust
governor.advance(&fitness);
```

`Governor::breed_next_generation` still uses unseeded randomness for later-generation config mutation and crossover paths. The relevant code in `crates/xagent-sandbox/src/governor.rs` includes:

```rust
mutate_config_with_strength(&mut cfg, mutation_strength, self.mutation_strategy);
```

and:

```rust
let mut rng = rand::rng();
```

The new test `seeded_ab_arms_are_paired` validates helper-level determinism, but it does not run the actual headless multi-generation A/B harness twice and prove identical results for the same seed. It therefore cannot catch unseeded generation-two-and-later divergence.

**Why It Matters**

The speed-decoupling gate is supposed to decide whether a new fitness mode reduces speed exploitation. If the A/B arms are not truly paired across generations, the gate can pass or fail due to random drift rather than the fitness change. This matters more as selection pressure accumulates across generations.

**Prior-Report Comparison**

The 2026-06-18 GPT-5, Gemini, and Claude reports all raised uncontrolled or insufficient A/B validation as a high-priority issue. The recent changes address the surface of that finding but leave a core reproducibility gap.

**Recommended Path**

- Thread a deterministic RNG through governor breeding during validation mode.
- Avoid all direct `rand::rng()` calls inside validation-sensitive paths.
- Add a black-box determinism test:
  - Run `run_headless_with_flags` twice with the same validation seed and flags.
  - Assert identical summary metrics and generation outputs.
  - Run enough generations to exercise breeding and crossover, not just initial mutation.
- Persist the validation seed and effective config in the output artifact.

### F3 - P2 - Correlation Gate Accepts Strongly Negative Baselines

**Evidence**

`crates/xagent-sandbox/src/headless.rs` sets:

```rust
let baseline_corr_exploitable =
    baseline.speed_fitness_correlation.abs() >= BASELINE_CORR_MIN;
```

But the gate criteria text says:

```text
baseline speed-fitness correlation must be strongly-positive
```

Using `abs()` means a strongly negative correlation passes the "baseline is exploitable" precondition. In that regime, speed is already harmful rather than exploitable, so the interpretation is inverted.

**Why It Matters**

This is a semantic gate bug. It can produce a misleading approval message in exactly the cases where the experiment should say, "speed exploitation was not present in the baseline, so this gate is not meaningful."

**Prior-Report Comparison**

This is a residual issue from the broader speed-decoupling gate criticism in the 2026-06-18 reports. The gate became stricter, but the sign semantics still need cleanup.

**Recommended Path**

- Replace `abs() >= BASELINE_CORR_MIN` with `>= BASELINE_CORR_MIN` for the baseline exploitability check.
- Use signed improvement where the hypothesis is "positive speed correlation falls."
- Keep absolute-value checks only for secondary "magnitude changed" diagnostics.
- Add one unit test with a strongly negative baseline correlation and assert the gate refuses to call it a speed-exploit fix.

### F4 - P2 - Planning-Reference Scrub Is Partial, Not Complete

**Evidence**

Plan 0011 reduced planning references and ratcheted the guard baseline, which is a useful improvement. However, many references remain in live source, tests, and shaders.

Examples found with a source-focused search include:

- `crates/xagent-shared/src/config.rs`: many comments still reference plan numbers and workstream/layer terminology.
- `crates/xagent-sandbox/src/agent/mod.rs`: remaining planning/workstream references in source comments.
- `crates/xagent-brain/src/buffers.rs`: several plan and layer references.
- WGSL files such as `crates/xagent-sandbox/src/shaders/common.wgsl`, `kernel_tick.wgsl`, and `phase_physics.wgsl`: multiple plan/workstream references remain.
- Tests still contain many plan-specific names and comments.

The guard currently passes because it is ratcheted, not because the source is fully plan-agnostic.

**Why It Matters**

Plan references in source make code harder to evolve. Future contributors should not need to read an old implementation plan to understand a field or shader constant. These references also signal that temporary implementation scaffolding has become permanent documentation.

**Prior-Report Comparison**

This directly follows the 2026-06-18 Grok/Gemini criticism that source files carried too much planning-process vocabulary. Plan 0011 addressed the problem but did not finish it.

**Recommended Path**

- Define the policy precisely:
  - Plan references allowed in `docs/plans`.
  - Historical notes allowed in review reports.
  - Runtime source and shaders should explain behavior in domain terms.
  - Tests may reference regression IDs only when that improves traceability.
- Continue ratcheting until only intentional exceptions remain.
- Consider a small allowlist file so the guard distinguishes accepted historical regression labels from ordinary source comments.

### F5 - P2 - Hidden `.claude` Workflow Is Significant Untested Operational Code

**Evidence**

Recent work added `.claude/workflows/implement-plan.js`, an 889-line workflow engine, plus `.claude/skills/implement-plan/SKILL.md`. This code is hidden from ordinary `rg --files` output unless `--hidden` is used.

The workflow performs branch and worktree orchestration and includes destructive operations:

- Setup deletes branches matching `implement-plan/${PLAN}*` using `branch -D`.
- Worktree creation removes stale worktrees and branches using `worktree remove --force` and `branch -D`.
- Integration cleanup deletes scratch branches similarly.

`node --check` passes, so the file is syntactically valid. There is no dedicated behavioral test suite for parsing, branch matching, dry-run output, or failure recovery.

**Why It Matters**

This is not just documentation. It is operational code that can delete local branches and worktrees. Its blast radius is different from the Rust simulation code and should be tested as automation. The project needs confidence that this helper cannot delete the wrong branch, silently skip a required review gate, or leave the repository in a confusing state.

**Prior-Report Comparison**

This is new risk introduced after the previous review batch. It also continues the broader theme that process automation is becoming part of the product surface.

**Recommended Path**

- Split the workflow into importable JS modules with pure functions for parsing, branch selection, and command planning.
- Add unit tests for branch matching, command planning, and failure cases.
- Add a dry-run mode that prints exact commands without executing them.
- Avoid broad pattern deletion. Delete exact refs created by the workflow, or require explicit confirmation for wildcard branch cleanup.
- Add this workflow to CI at least via `node --check` and a focused unit test command.

### F6 - P2 - Tests Often Pin Current Proxy Behavior Rather Than Intended Behavior

**Evidence**

The repository has many more tests than earlier snapshots, and the local sandbox test suite passed. That is a strength. The issue is that several recent tests protect current numerical outputs rather than higher-level intent.

Examples:

- `fitness_calibration_replay_profiles` asserts the camper effort score is below 1.0, but does not assert competent-forager beats camper.
- The same test prints an explanation that is internally stale: it says the competent composite is held down by exploration `0.6` and survival `0.75`, but those values do not explain the printed composite `0.3209`.
- `competent_forager_saturates_foraging_on_real_scale` proves one high-skill synthetic profile saturates foraging, but does not test duration invariance or anti-camping ranking.
- `seeded_ab_arms_are_paired` proves helper determinism, not full validation determinism.

**Why It Matters**

A large test suite can create false confidence if the tests encode accidental behavior. For this project, the critical acceptance criteria are behavioral and statistical. The tests need to reject proxy gaming, not merely stabilize proxy values.

**Prior-Report Comparison**

Previous reports repeatedly asked for falsifiable acceptance criteria. Recent changes added more falsifiability, but the assertions are still too close to implementation details in the most important areas.

**Recommended Path**

- For every default-flip candidate, write one invariant test, one anti-proxy test, and one regression test.
- Separate snapshot-style calibration tests from behavioral acceptance tests.
- Require acceptance tests to state the intended biological or behavioral interpretation in comments.
- Add negative controls: intentionally bad profiles should fail the same gates that good profiles pass.

### F7 - P2 - Original Behavioral Goal Remains Unproven

**Evidence**

The original direction of the project is emergent cognition through homeostasis, predictive processing, and self-organized behavior rather than conventional reward functions. The current architecture is closer to supporting that than earlier versions, but the behavioral evidence is still weak.

Relevant long-lived signals:

- The status docs for prior learning plans record that learning probes remained at chance baseline.
- The README and evolution journey still discuss chance-level mirrored steering and an open credit-learning bottleneck.
- Integration tests include chance-baseline learning probes, and those tests pass.
- Recent fitness work mostly changes outer-loop selection pressure. It does not prove within-life learning, predictive coding, or robust food/hazard competence.

**Why It Matters**

This is the central forward-looking question: how close is the project to its original goal? Mechanically, the substrate is much closer than it was in April. Behaviorally, it remains early and unproven. The project should plan for research and validation work, not just routine maintenance.

**Prior-Report Comparison**

This issue appears across April and June reports in different forms: docs drift, chance-level learning probes, poor throughput, and proxy-fitness risk. Recent plans have improved the scaffolding but have not closed the behavioral gap.

**Recommended Path**

- Treat "learning food seeking" and "danger avoidance" as separate measured capabilities.
- Create a small fixed benchmark suite:
  - Static food gradient.
  - Moving food gradient.
  - Hazard avoidance with no food.
  - Combined food/hazard tradeoff.
  - Generalization to shifted seed/layout.
- Report medians and confidence intervals across seeds.
- Keep default flags conservative until behavior beats chance and anti-proxy controls under this suite.

**Why It Matters**

This is lower risk than the fitness and validation issues, but it affects onboarding and future development. Readers trying to extend the system will use these docs to form a mental model. Contradictory docs slow that down and increase the chance of accidental wrong changes.

**Prior-Report Comparison**

The April reviews found severe stale architecture documentation. Most of that has been addressed. This is residual cleanup, not a major blocker.

**Recommended Path**

- Update `crates/xagent-shared/README.md` so `SensoryFrame`/`SensoryEncoder` are clearly labeled as compatibility, test, or historical API surfaces.
- Add a brief "live tick path" diagram that names only current runtime components.
- Link legacy APIs to their actual consumers.

## Original Goal Alignment

### Original Goal As Understood

The project aims to build an agent whose useful behavior emerges from homeostatic pressure, predictive processing, embodied sensing, and evolutionary selection, rather than from a conventional hand-authored reward policy. The target behaviors include food seeking, survival, hazard avoidance, exploration, and eventually learning or adaptation that generalizes beyond one seed or layout.

### Current Mechanical Alignment

Mechanical alignment is moderate to strong:

- The live runtime is GPU-centered and more honestly documented.
- Brain and sandbox crates are more clearly separated.
- Telemetry surfaces are richer and better tested.
- CI enforces formatting, linting, checking, and a large sandbox test suite.
- Recent plans created more explicit validation criteria.

This gives a credible substrate for continued research.

### Current Behavioral Alignment

Behavioral alignment is still weak or unproven:

- Existing learning probes remain described as chance-level.
- Recent intent-aware fitness is an outer-loop selector, not direct evidence of within-life cognition.
- The latest effort fitness still allows proxy success through survival/camping.
- Visual cortex and danger-aware paths are still gated by default due throughput and validation concerns.

The project has not drifted into an ordinary supervised-learning system, which is good. It has drifted into a mode where process, proxy fitness, and validation machinery can look more complete than the actual emergent behavior.

### Forward Effort Estimate

Expected effort to maintain and advance:

- **Short-term stabilization:** 2-4 weeks for an experienced Rust/GPU engineer to fix validation determinism, repair effort-fitness invariants, clean docs, and test `.claude` workflow behavior.
- **Credible default flip for effort/danger flags:** 4-8 additional weeks, assuming experiment runtime is manageable and results are not contradictory.
- **Original behavioral proof:** open-ended research effort. A realistic estimate is 2-3 months to establish a defensible benchmark suite and determine whether the current architecture can beat chance consistently, longer if GPU throughput or credit assignment remains limiting.

## Missing Pieces

The main missing pieces before confident forward progress are:

1. A mathematically coherent fitness contract.
2. Fully deterministic paired validation for any A/B graduation gate.
3. Behavioral acceptance tests that reject camping and speed exploitation.
4. A fixed benchmark suite with seed distributions and confidence intervals.
5. Tested workflow automation for `.claude`.
6. A final source scrub that removes plan vocabulary from runtime comments or explicitly allowlists it.
7. Updated shared README language for live vs legacy sensory APIs.
8. Reduced shader-composition risk, or at least stronger shader build/render validation.

## Suggested Pathway

### Phase 1 - Stabilize Measurement Contracts

Timebox: 1-2 weeks.

- Rewrite effort-fitness formulas or documentation so they agree.
- Add duration-invariance, anti-camper, and competent-vs-fast controls.
- Fix the signed speed-correlation gate.
- Add a black-box deterministic validation test that exercises multiple generations.

Exit criteria:

- Same-seed validation reruns produce identical metrics.
- Camper no longer outranks competent forager unless explicitly justified.
- Gate text, code, and tests agree on signed correlation semantics.

### Phase 2 - Make Graduation Evidence Defensible

Timebox: 2-4 weeks.

- Rerun effort-fitness and danger-avoidance validation after Phase 1.
- Store seeds, configs, summaries, and statistical intervals.
- Require both positive controls and negative controls.
- Keep flags off by default until the evidence is reproducible.

Exit criteria:

- Default-flip proposals include paired runs, seed lists, effect sizes, and failure cases.
- Validation artifacts are reproducible by command, not only by prose.

### Phase 3 - Clean Forward Development Surfaces

Timebox: 1-2 weeks.

- Finish the plan-reference scrub or formalize exceptions.
- Update stale shared README sections.
- Add tests for `.claude/workflows/implement-plan.js`.
- Add a documented dry-run mode for operational workflow commands.

Exit criteria:

- Future contributors can understand live runtime flow without reading old plans.
- Workflow automation can be tested without touching real branches/worktrees.

### Phase 4 - Re-Anchor On Original Behavior

Timebox: 4-8 weeks.

- Build the benchmark suite around food seeking, hazard avoidance, and generalization.
- Keep separate metrics for within-life learning, evolutionary selection, survival, and exploration.
- Compare against chance, simple hand-coded baselines, and current legacy flags.
- Decide whether current architecture is promising enough to continue or needs a larger redesign.

Exit criteria:

- The project can state what behavior has emerged, under what seeds, at what confidence level.
- The benchmark suite distinguishes real competence from proxy success.

The recent changes show good engineering intent and have addressed several prior findings, but the most important project risk remains: proxy metrics can still look successful while the original emergent-behavior goal remains unproven.

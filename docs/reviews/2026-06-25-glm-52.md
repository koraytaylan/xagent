## Executive Verdict

The 0012–0018 sequence is the most intellectually honest stretch in the project's history. Three consecutive plans (0013, 0017-WS0001, 0018) ran prove-or-kill gates and **recorded negative results instead of moving the goalposts** — the instinct priors, the TD-decay/urgency credit fix, and all three credit-mechanism attacks (auxiliary loss, frame-sync trace, gradient-variance shaping) were falsified against the 0.62/0.70 steering gate and shipped no mechanism. The 0012 homeostasis-only restoration closed the deepest purity breach the 2026-06-18 reviews identified (the always-on approach-PBRS term in `raw_gradient`), and 0014 fixed the three confirmed defects those reviews surfaced (camper inversion, CI all-skip, death-path TD divergence). Process discipline is now genuinely ratcheted: the contributing guard holds, no TODO/FIXME anywhere in `crates/`, prototype shader changes from falsified spikes were reverted from `develop` rather than left behind flags.

The project is, however, now carrying a **deeper scientific problem than the reviews diagnosed**, and two **mechanical gate-integrity regressions** landed in the last week that the process did not catch.

1. **The credit-path bottleneck is now triple-falsified and the steering-alignment goal is not closer than it was on 2026-06-19.** 0017 proved trace-decay/urgency isolation don't work; 0018 proved auxiliary loss, frame-sync trace decay, and gradient-variance normalization don't work. The sharpest 0018 result — TD-error normalization amplifies mean|δ| `4.5e-4 → 0.18` (~400×) yet steering stays at `0.498` — is a genuinely valuable negative: it localizes the bottleneck to **credit alignment** (timing + direct supervision), not magnitude. But "carried to plan 0019" is the third carry-forward of the same bottleneck in two weeks, and every gate the project set for itself (0.62, then 0.70) is still above the measured band. The platform is converging on a high-fidelity *measurement harness for a learning signal it cannot produce*.

2. **A `cargo fmt --check` failure is committed to `develop`** in the most recent commit (`1da6e0f5`), whose message claims "cargo fmt/clippy/test green." The CI gate CONTRIBUTING.md names first is therefore red on the canonical tree. This is a machine-gate regression, not a judgment call.

3. **The 0017 cortex-throughput "✅ Done" is overstated.** The ≥50%-of-baseline budget the SCOPE committed is **not achieved on the target hardware**: the committed `CORTEX-PROFILE-BASELINE.txt` records cortex ON at ~83 tps vs ~7,625 tps baseline (~1.1%, ~93× slower) on Metal. The `cortex_throughput_meets_budget` test passes only because it was made to **skip on real GPU hardware** and assert solely on lavapipe. The roll-up STATUS row "≥50% throughput budget asserted on CI" is technically true and materially misleading.

Forward effort remains medium-high. The mechanical substrate is strong and the falsification discipline is exemplary; the binding constraint is no longer engineering quality, it is that the central research hypothesis (emergent vision→action steering under homeostasis-only credit) has resisted every mechanism tried and has no remaining candidate with a measurement-backed reason to expect it to work.

### F1 - P1 - `cargo fmt --check` fails on `develop`; commit claims "fmt green"

**Evidence**

The most recent commit `1da6e0f5` (perf: vision as GPU texture) lands `crates/xagent-sandbox/src/ui.rs:1142-1145` with two assignments that `rustfmt` wants to collapse:

```rust
let ctx = cols[0].ctx().clone();

    egui::Id::new(("agent_vision", effective_snap.id, vw, vh));
let existing =
    ctx.data(|data| data.get_temp::<egui::TextureHandle>(tex_key));
```

`cargo fmt --all -- --check` against the committed tree produces:

```text
Diff in crates/xagent-sandbox/src/ui.rs:1139:
-                    let tex_key =
-                        egui::Id::new(("agent_vision", effective_snap.id, vw, vh));
-                    let existing =
-                        ctx.data(|data| data.get_temp::<egui::TextureHandle>(tex_key));
+                    let tex_key = egui::Id::new(("agent_vision", effective_snap.id, vw, vh));
+                    let existing = ctx.data(|data| data.get_temp::<egui::TextureHandle>(tex_key));
```

The commit message's closing "cargo fmt/clippy/test green" line is inaccurate for the committed tree (the perf commit has no such line, but the 0018 commit `d1c46811` does claim "cargo fmt/clippy/test green (242 tests, GPU on Metal)"). Either the author ran `cargo fmt` without `--check` (which formats in place and reports success), or CI did not run on this commit before it landed on `develop` (the branch is 6 commits ahead of `origin/develop`, so the remote CI gate has not seen it).

**Why It Matters**

CONTRIBUTING.md lists `cargo fmt --all -- --check` as the **first** merge gate, enforced by CI. A red fmt gate on `develop` means either the local pre-push gate was skipped or CI has not run. This is the cheapest gate to satisfy and the one most indicative of process discipline; failing it undermines the "ratchet holds" claim that the rest of the review relies on. It is also the kind of defect a reviewer-checklist pass should have caught, since the REVIEW-CHECKLIST explicitly trusts the machine gate.

**Prior-Report Comparison**

No prior report found a committed fmt failure. The 2026-06-19 reviews praised the green-gate discipline. This is a regression on the project's strongest axis.

**Recommended Path**

- Run `cargo fmt --all` and amend or follow-up-commit `ui.rs` before pushing to `origin/develop`.
- Verify CI actually ran on `1da6e0f5` before it reached `develop`; if CI is not gating pushes to `develop` locally, that is the real bug.
- The perf commit was not routed through `implement-plan` (no plan owns it); consider whether unscoped commits should require the same fmt/clippy pre-flight the workflow enforces.

### F2 - P1 - 0017 Cortex "✅ Done / ≥50% Budget" Overclaimed; Test Skips on Real GPU

**Evidence**

Plan 0017 SCOPE committed: "Optimize visual-cortex throughput to bring it within the ≥50% budget (currently 0.24%) without breaking existing orientation/invariance probes." The roll-up `docs/plans/STATUS.md` row says "WS0002 cortex throughput (complete) ... ≥50% throughput budget asserted on CI." The 0017 STATUS.md marks WS0002 "✅ Done."

The committed `docs/plans/0017-.../CORTEX-PROFILE-BASELINE.txt` records the real-GPU measurement:

```text
- Cortex OFF (fused baseline): ~7,625 tps (131.14 μs/frame)
- Cortex ON — all stages:        ~83 tps (12,117 μs/frame), 98.92% overhead
- cortex ON is ~93× slower than cortex OFF
```

That is **~1.1% of baseline**, ~45× below the ≥50% target, on the target hardware (Metal). The acceptance test `cortex_throughput_meets_budget` (`integration.rs:703`) was written to skip exactly this case:

```rust
if !xagent_brain::GpuKernel::is_software_adapter() {
    eprintln!(
        "Skipping cortex_throughput_meets_budget on GPU hardware adapter: \
         warp underutilization (18/256 active lanes = ~7%) makes the ≥50% \
         criterion unachievable without workgroup restructuring (out of scope). \
         This test runs and asserts only on CPU software adapters (lavapipe/CI)."
    );
    return;
}
```

So the gate "asserts on CI" (lavapipe) and **silently skips on every real GPU**. The optimization did not achieve its budget on the hardware the project actually runs on; the test was redefined to pass on the only environment where the number is achievable, and the STATUS row reports this as "Done."

**Why It Matters**

This is the same class of defect the 2026-06-19 reviews (opus H4) called out for CI silently skipping the GPU suite: a gate that skips on the relevant hardware is not a gate, it is a green checkbox. The cortex is the load-bearing subsystem for the entire 0017–0018 emergence line of work; if its throughput budget is unmet by ~45× on real GPU, the planned encoder A/B (0017-WS0004, "superseded") and any default flip are blocked for a reason the STATUS does not surface. A reader of STATUS.md will conclude the cortex is production-viable at 50% throughput; a reader of the baseline txt will conclude it is at 1.1%. Those are inconsistent.

The hardware-skip rationale (256-lane workgroup, 18 active threads, ~7% lane occupancy) is real and well-documented in `gpu_kernel.rs:492-503`. But that means the **optimization was structurally unable to hit the budget** and the plan should have recorded a miss, not a done.

**Prior-Report Comparison**

The 2026-06-19 reviews flagged CI all-skip (0014 fixed it for the GPU suite) and the brain-pass latency ceiling (unchanged). This is a new instance of the same pattern: a throughput gate that skips the environment where it fails. It is more material than the CI all-skip because it hides a 45× miss behind a passing row.

**Recommended Path**

- Change the 0017 STATUS WS0002 row and the roll-up to state the truth: "Cortex throughput optimized but **did not meet ≥50% budget on GPU hardware** (~1.1% of baseline on Metal, ~93× slower); the ≥50% assertion holds only on lavapipe. Blocking on workgroup restructuring (out of scope)."
- Either keep the test skipping on GPU (acceptable, given the structural limit) but rename it `cortex_throughput_meets_budget_on_software_adapter` so the name does not claim a generality the body avoids, or add a separate **failing-on-purpose** GPU test that documents the real-GPU fraction as a known-regression pin (so the 1.1% number is tracked, not hidden).
- Do not mark a throughput workstream "Done" when the budget is met on 1 of 2 target environments and missed by 45× on the other.

### F3 - P1 - Credit-Path Steering Goal Triple-Falsified; Third Carry-Forward

**Evidence**

The 0017 SCOPE committed to "steering alignment rises measurably above chance (≥0.70 target)." Measured outcomes:

- 0017-WS0001: TD trace-decay `0.99` + urgency isolation → alignment `0.441` vs `0.489` baseline (chance band `[0.38, 0.62]`). Falsified, reverted.
- 0018-0001 auxiliary steering loss: `0.509` (chance). REJECT.
- 0018-0002 frame-synchronized trace decay: `0.501` (chance, and behaviorally untested at `vision_stride=1`). REJECT.
- 0018-0003 gradient-variance shaping: `0.498` (chance). REJECT.

The 0018 STATUS records "Credit-path bottleneck carries to plan 0019." The 0017 STATUS already carried it to 0018. The 2026-06-19 claude-opus review localized the bottleneck (H1/H2: turn channel cannot accumulate sign-correct credit). Two plans and four mechanism attacks later, the measured alignment has not left the chance band `[0.38, 0.62]` and the gate has not moved.

The one genuinely valuable 0018 result is the gradient-shaping falsification: normalizing TD error amplified mean|δ| `4.5e-4 → 0.18` (~400×) with **no steering change**. That is a strong, falsifiable negative that rules out magnitude as the bottleneck and points to **credit alignment** (timing + direct supervision). This is the kind of negative result the process is designed to produce, and it is recorded honestly in `0003-GRADIENT-SHAPING-DECISION.md`.

**Why It Matters**

This is the central research question, not a side issue. The project's README vision is emergent cognition from homeostatic pressure; the load-bearing sub-claim is that vision→action steering becomes learnable under TD(λ) credit. After 0017/0018, every mechanism tried (decay schedule, urgency isolation, auxiliary loss, frame-sync traces, gradient normalization) has failed, and the failure mode is consistent: the encoder separates food-left/right (raycast cosine-diff 0.0036 ~18–24×, Gabor 0.964 ~55×), but the policy cannot route that separable signal to the turn channel. "Carry to 0019" without a new hypothesis class is process-as-usual masking a stuck research program.

The 0018 auxiliary-loss spike (F5) and frame-sync spike also show the limits of the spike-then-revert discipline: the auxiliary loss was tested as a **CPU overlay with no GPU gradient injection**, so "0.509" is not actually a falsification of auxiliary loss as a mechanism — it is a falsification of measuring it that way. The real test (GPU-integrated auxiliary loss) was never run.

**Prior-Report Comparison**

The 2026-06-19 gpt-5-codex F7 and grok-43 "learner strength" theme both flagged "behavioral goal unproven, learning probes at chance." This review confirms it is **still** unproven and now triple-falsified. The honest negative recording is a process improvement; the lack of a path forward is the unchanged risk.

**Recommended Path**

- Stop carrying the same bottleneck to a new plan number without a new hypothesis class. The next plan should either (a) name a mechanism not yet tried with a measurement-backed reason to expect it to work (e.g., direct GPU-injected auxiliary supervision, which 0018-0001 explicitly did not test), or (b) step back and question whether TD(λ) actor-critic with eligibility traces over a 10-tick vision latency is the right credit structure at all.
- Run the auxiliary-loss mechanism on the GPU before calling it falsified. The 0018-0001 REJECT is a falsification of a CPU overlay, not of auxiliary self-supervision as a mechanism.
- Re-examine the 0018-0002 frame-sync result: it is "disabled at vision_stride=1" so the probe (`vision_stride=1`) never exercised it. That spike was not actually tested under its own activation condition.
- Consider whether the 0.70 gate is the right target, or whether an intermediate "reliably above 0.62 with CI excluding chance" gate would surface partial progress that the current all-or-nothing gate hides.

### F4 - P2 - 0013 Prove-Or-Kill A/B Harness Has No Regression Test

**Evidence**

Plan 0013's locked decision (point 5) makes a headless A/B benchmark the prove-or-kill criterion. The harness `run_innate_instinct_ab` was implemented in `crates/xagent-sandbox/src/headless.rs:492` and the gate was run once on local Metal (10 gens, pop 10), producing the FAILED verdict recorded in `0013-INNATE-INSTINCT-DECISION.md` (survival +0.19%, food-per-death 0.37, alignment 0.000).

A repo-wide search for callers of `run_innate_instinct_ab` outside `headless.rs` returns **none**:

```text
$ rg -rn "run_innate_instinct_ab" crates/
crates/xagent-sandbox/src/headless.rs:492:fn run_innate_instinct_ab(
```

There is no integration test that invokes the harness. The gate ran manually, once, and the result lives only in a decision doc. The harness itself (the thing that would re-run the gate if the credit path or instinct seeding changed) has no test guarding it against rot.

**Why It Matters**

This is the same "falsifiable gate with no regression test" pattern the 2026-06-19 reviews flagged for the speed-decoupling harness. A prove-or-kill gate that runs once and is then orphaned cannot catch a future regression in the harness logic, and cannot be re-run mechanically when the underlying learning signal changes (which 0012/0015/0017/0018 all changed). The 0013 verdict "gate FAILED, flag stays off" is currently unfalsifiable by anyone who did not run the original Metal job.

**Prior-Report Comparison**

The 2026-06-19 gpt-5-codex F2 criticized partially-paired A/B validation. This is a stricter version: the A/B harness exists but is not wired into any test. The 0014 CI/lavapipe work made the **GPU suite** run on CI, but `run_innate_instinct_ab` is not part of that suite.

**Recommended Path**

- Add a test (GPU-gated, self-skip without an adapter) that calls `run_innate_instinct_ab` with a tiny generation count and asserts the harness produces well-formed `ValidationStats` (not that it passes the gate — the gate legitimately failed). This guards the harness logic without re-asserting the negative verdict.
- Alternatively, if the harness is considered one-shot and not reusable, delete it and keep only the decision doc — but then the 0013 STATUS should not list the harness as a landed deliverable.

### F5 - P2 - 0018 Auxiliary-Loss Spike Is a CPU Overlay; "Convergence" Test Doesn't Test GPU Learning

**Evidence**

`auxiliary_steering_loss_converges_on_bearing` (`integration.rs:8806`) computes an L2 loss between the GPU's turn output and the food bearing each tick, asserts `late < early` (the loss decays), and passes. The test's own comments (lines 8883–8886, 8912–8914) state:

```text
The auxiliary loss in this spike is a CPU-side measurement overlay — it
does NOT inject gradient updates into the GPU kernel. The GPU kernel learns
only via its existing TD(λ) credit path.
```

So the "convergence" is the CPU recomputing a loss on the GPU's outputs; nothing feeds back. The companion `auxiliary_steering_probe_with_loss_enabled` then measures steering at `0.509` (chance) and records REJECT. The decision doc `0001-AUXILIARY-LOSS-DECISION.md` honestly notes "injects no GPU weight updates; steering 0.509 ... Needs GPU-side integration to truly test."

**Why It Matters**

The 0018-0001 REJECT is recorded as a falsification of "auxiliary steering loss" as a mechanism. It is not. It is a falsification of "the existing TD path under a CPU measurement overlay." The actual mechanism (an auxiliary self-supervised loss that **does** inject a vision→action gradient into the GPU weights) was never built or tested. A reader of the 0018 STATUS ("auxiliary steering loss: REJECT ... Direct-supervision loss converges in a CPU-side harness (-68.5%) but injects no GPU weight updates") gets the caveat, but the roll-up "3/3 REJECT" framing makes it easy to cite as "auxiliary loss failed" when the truthful statement is "auxiliary loss was not tried at the level that could have worked."

The convergence test itself (`late < early`) is also weakly falsifiable: a CPU-side loss computed on outputs that drift toward a target as the agent happens to rotate will decay without any learning. Deleting the GPU kernel would not necessarily break `late < early` if the arena's initial geometry already biases turns toward food.

**Prior-Report Comparison**

The 2026-06-19 reviews praised the move from print-only to asserting tests. This spike's assertions are technically present but test the overlay, not the mechanism — a new form of the "test the right thing" concern.

**Recommended Path**

- If auxiliary self-supervision is in scope for 0019, the GPU-integrated version must be built before any REJECT is recorded against the mechanism. The 0018-0001 result should be framed as "mechanism not tested at the relevant level," not "mechanism falsified."
- The convergence test should either (a) assert something that breaks if the GPU stops dispatching (e.g., that food is consumed, or that turn outputs change across ticks), or (b) be renamed to `auxiliary_steering_loss_overlay_decays_on_gpu_outputs` so the name does not imply learning.
- Apply the same scrutiny to 0018-0002 (frame-sync trace decay "disabled at vision_stride=1" so the probe never exercised it): that is also "mechanism not tested under its activation condition," not a clean falsification.

### F6 - P2 - Diagnostic Print Tables Persist in Probes

**Evidence**

`cortex_throughput_profile_baseline` (`integration.rs:658`) prints a large structured table under `--nocapture` and asserts nothing (it is a measurement-record test). `baseline_td_error_variance_during_foraging`, `gradient_variance_per_context_breakdown`, and the auxiliary-loss probes all print diagnostic tables alongside their (real) asserts. The budget test is silent only because it skips on Metal; on lavapipe it prints the baseline/cortex/fraction line.

The 2026-06-19 grok-43 review explicitly recommended: "Either drop the prints or gate them behind an env var so the test is silent and purely falsifying by default." This was done for `fitness_calibration_replay_profiles` (per gpt-5-codex 2026-06-19 F6) but not for the new 0017/0018 probes.

**Why It Matters**

Low severity. The new probes are genuinely falsifiable (they assert real invariants, not just print). But the project's own REVIEW-CHECKLIST asks that tests "assert invariants rather than filtering out violations," and a test that both asserts and prints a large table is harder to read for the falsifying line. On CI with `--nocapture` these tables add noise.

**Prior-Report Comparison**

Direct continuation of the 2026-06-19 "non-falsifiable calibration test" theme. The 0010/0014 work addressed it for fitness; the 0017/0018 probes reintroduced the print-table pattern for cortex/credit diagnostics.

**Recommended Path**

- Gate the diagnostic `eprintln!` tables behind an env var (e.g. `XAGENT_VERBOSE_PROBES`) so the tests are silent and falsifying by default, with the table available on demand.
- Or move the tables into the decision-doc / baseline-txt artifacts only and keep the test bodies assertion-only.
